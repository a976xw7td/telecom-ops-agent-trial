# 经营决策 Agent —— 可运行应用与证据验证

一个**双击就能打开、断网也能用**的电信区县经营决策应用：把一份周报变成可复核的判断，
每一条结论都能追到「哪个指标、哪条规则、哪份文档」，AI 不负责下结论，人负责拍板。

> 本交付为**测试账号试点**，使用脱敏构造的 4 周（2026-W40 ~ W43）× 3 个区县样本数据。
> 所有数字与结论仅用于验证流程与证据链，不代表任何真实经营情况，其他同学无需参与。

## 四、数据边界（先讲清楚不能做什么）

- **数据是构造样本**：4 周、3 个区县、7 个指标，用于演示证据链，不是真实经营数据。
- **指标口径固定**：`bbNetAdd`、`churnRate`、`fusionPen`、`arpu`、`complaints`、
  `installBacklog`、`channelOrders`，单位与算法写在 `data.js` 的口径里。
- **明确标注"本样本未接入"的字段**：外协成本、竞品降价幅度、5G 专网明细等。
  问到时 Agent **不做估算**，直接返回缺口说明（见 `T3-gap-list`）。
- **不做预测**：What-if 是"假设增员 N 人后的机械推演"，不是经营预测；
  首周按 50% 产能爬坡，第 2 周起满产，人均 6 单/人日。
- **人工确认边界**：8 条行动方案全部标注需人工确认后才对外执行，
  Agent 不自动派单、不自动联系客户、不自动改承诺口径。

## 五、四类资产是怎么串起来的

这是本试点最想验证的一点：**Agent / Skill / RAG / 工作流不是四个并列的名词，而是一条有方向的链**。

### 工作流（9 步，固定顺序，每步留痕）

| 步骤 | 做什么 | 在哪实现 | 可观察输出 |
|---|---|---|---|
| 1 输入校验 | 周期/区县/序列是否齐 | `engine.getRegion` | 缺失即拦截并说明 |
| 2 意图路由 | 这问题该走哪条路径 | `agent.detectIntent` | 诊断/指标/检索/超范围 |
| 3 证据边界检查 | 问的字段样本里有没有 | `engine.dict` | 无则标「本样本未接入」 |
| 4 RAG 检索 | 取口径/规则/案例原文 | `engine.retrieve` | `D6#2` 这类可回溯引用 |
| 5 指标计算 | 算 7 个指标与趋势 | `engine.metrics` | 指标表 + 环比 |
| 6 原因假设排序 | 多假设按置信度排队 | `engine.diagnose` | P1…P4 + 权重 |
| 7 证据闸门 | 证据够不够下结论 | `engine.diagnose` | 够→已归因；不够→降级 |
| 8 行动方案 | 每条带验证指标与风险 | `engine.actions` | A1…A8 |
| 9 结构化输出 | 答案 + 运行记录可导出 | `agent.run/answer` | 同输入 → 同文件 |

### Skill 层（`skill.js`，版本 1.0.0）

- **purpose**：把周报转成可复核的结构化判断、原因假设与带验证指标的行动方案，**并在证据不足时拦截**。
- **必填输入**：`report.period`（周期口径）、`report.regions[].series`（≥2 周才判趋势）、`report.weeks`（趋势窗口）。
- **可选输入**：`installStaff` 等 —— **缺失时降级**，把相关结论改写为"待补数据后再判断"，不硬算。
- **人工确认边界**：涉及对外承诺变更（SLA/口径/价格）、增员外协等资源投入、证据闸门 blocked 三种情况，
  必须人工确认。`alwaysHumanOwned` 明确写了三件永不由 Agent 决定的事：
  **是否采纳建议、资源投入决策、对外口径与价格调整**。
- **失败语义**：证据不足 → 输出缺口清单不替代推断；缺可选字段 → 标注降级；越界区县 → 拦截并说明样本范围。

### RAG 层（`kb.js`，8 份文档 D1–D8）

- 文档按空行切块，块号从 **1** 开始；引用格式固定 `文档号#块号`，如 `D6#2`。
- 检索按词面得分排序返回候选块，**答案里每个论断必须挂引用**；引不出就进证据闸门拦截。
- 文档类型覆盖：指标口径（D1）、装维规则（D2）、融合政策（D3）、渠道（D4）、投诉分类（D5）、
  历史案例（D6）、字段清单（D7）、人员产能（D8）。

### Agent 层（`agent.js`，版本 1.0.0）

对外只有 5 个出口：`detectIntent`、`run`、`answer`、`rank`、`versionId`。
**没有自由发挥的模板**：每句话要么来自数据、要么来自文档，要么明确说是缺口。

## 六、7 条检查规则（Skill 的判断标准，全部可复算）

| 规则 | 指标 | 阈值 | 级别 | 含义 | 依据 |
|---|---|---|---|---|---|
| C1 | `churnRate` | ≥ 1.50 | 高 | 离网率触碰红线 | D1 |
| C2 | `installBacklog` | > 250 | 高 | 积压超清理阈值 | D2 |
| C3 | `complaints` | > 60 | 中 | 投诉超周阈值 | D5 |
| C4 | `fusionPen` | < 55.0 | 中 | 融合渗透率低于目标 | D3 |
| C5 | `arpu` | < 72.0 | 低 | 综合 ARPU 低于目标 | D1 |
| C6 | `bbNetAdd` | trend_down | 低 | 净增连续下滑 | D1 |
| C7 | `installBacklog` | cross_check | 中 | 积压增量口径核验 | D2 |

风险分 = 命中规则按级别加权求和（高 3 / 中 2 / 低 1），满分 14。

## 七、诊断实例：新港区（XG）

**问题**：新港区为什么离网率上升，我该怎么办？
**结论**：`state = 已归因`，风险分 **13 / 14**，命中 C1、C2、C3、C4、C5、C7 共 **6 条**。

### 4 条竞争假设按置信度排序（不预设答案）

| 假设 | 内容 | 依据 | 权重 | 置信度 |
|---|---|---|---|---|
| **P1** | 装维交付超时是投诉与离网主因（积压上升→工单超时→安装类投诉→合约窗口离网） | D2,D5,D6 | 最高 | **0.81** |
| **P4** | 在岗人数不足导致产能低于到达，积压无法自行下降 | D2,D8 | 0.85 | **0.77** |
| **P2** | 融合渗透率下滑削弱黏性，单宽带用户在合约到期窗口更易离网 | D1,D3 | 0.70 | **0.63** |
| **P3** | 渠道订单连续下滑削弱新增与存量触点，加速流失 | D4 | 0.50 | **0.45** |

注意 P1 与 P4 是**同一条因果链的两端**（需求侧 vs 产能侧），不是两个独立结论 ——
所以行动方案里两者必须一起做，只做一边会反弹。这是本应用特意保留的结构。

### 8 条行动方案（每条都有责任部门、时限、可验证指标、风险）

| 编号 | 行动 | 责任部门 | 时限 | 验证指标 | 主要风险 |
|---|---|---|---|---|---|
| A1 | P1 当日、P2 三日内清理，剩余排 P3 | 网络运营部 | 本周内 | P2 三日达成率 ≥ 95% | 挤压 P3，需同步排期 |
| A2 | 临时外协承接 P3 与部分 P2 | 网络运营部 | 1~2 周 | 积压周降 ≥ 100 单 | **外协成本口径未提供，收益无法测算** |
| A3 | 超时工单客户主动告知与改期 | 客户服务部 | 本周内 | 安装类投诉周环比下降 | 仅治表，须与 A1 同步 |
| A7 | 按边际递减补员/外协，首周按 50% 产能 | 网络运营部 | 1~2 周 | 日产能 ≥ 日均到达 | 新人爬坡，首周打折 |
| A8 | 同步上调 P2 承诺口径并显性告知 | 客户服务部 | 本周内 | 承诺兑现率不下降 | 口径需与市场部统一 |
| A4 | 装维上门随销融合套餐 A | 市场经营部 | 2~4 周 | 融合渗透率周升 ≥ 0.5pp | 折扣拉低当期 ARPU |
| A5 | 存量单宽定向外呼升级 | 市场经营部 | 2 周 | 外呼转化率 ≥ 3% | 转化低于随销，产能有限 |
| A6 | 连续两月低于基准 70% 的门店辅导复检 | 渠道管理部 | 2 周 | 门店订单回升至基准 85% | 需排除竞品促销干扰 |

**A2 的风险一栏是本交付的诚实点**：成本口径缺失，所以直接写"收益无法测算"，
而不是给一个编出来的 ROI。

## 八、What-if：增几个人才够？（可自己改数字复算）

XG 基准：在岗 18 人、日均到达 129 单、周积压 612 单、阈值 250 单、日均产能 108 单、净 **−21 单/日**。

| 增员 | 4 周积压曲线 | 是否降到阈值 250 以下 |
|---|---|---|
| +0 | 759 → 906 → 1053 → 1200 | 持续恶化 |
| +2 | 717 → 780 → 843 → 906 | 仍在恶化 |
| **+4** | **675 → 654 → 633 → 612** | **止住恶化，但降不下来** |
| +6 | 633 → 528 → 423 → 318 | 接近，仍不达标 |
| **+8** | **591 → 402 → 213 → 24** | **第 3 周达标** |

**结论（这正是"机械推演"的价值）**：让积压"不再涨"只要增 4 人，让积压"回到阈值内"要增 8 人。
中间这 4 人的差距，就是"看起来在改善"和"真正解决"的区别 —— 决策时要区分这两件事。

> 口径：人均 6 单/人日；新人首周按 50% 产能爬坡，第 2 周起满产；到达取多周均值。
> 这是假设推演，**不是经营预测**，成本与留存均未建模。

## 九、失败与降级：它什么时候会拒绝回答

这是"证据验证"里最容易被忽略、但最重要的一节。四种状态都能复现（见 T5 组 8 条测试）：

| 状态 | 触发 | 应用表现 |
|---|---|---|
| `attributed` 已归因 | 命中规则 + 证据充分 | 输出假设排序 + 行动方案（XG） |
| `unattributed` 异常未归因（已降级） | 有异常但证据不够 | **只说异常，不给原因结论**（CX） |
| `no_anomaly` 无异常 | 规则未命中 | 明确说"这周无需干预"（CD） |
| `off_topic` 超范围 | 问题不在样本内 | 拦截 + 说明样本范围，不猜 |
| 字段缺口 | 问到未接入字段 | 返回"本样本未接入"，**不估算** |

一个会拒绝回答的应用，比一个永远给答案的应用更可信 —— 这是本试点要验证的核心判断。

| 测试组 | 条数 | 验证什么 |
|---|---|---|

**为什么强调"可复算"**：所有测试只依赖 `assets/` 下的数据与规则文件，不调外部 API、不依赖随机数。同一份输入永远得到同一份输出，任何人 clone 后跑一条命令就能复现 —— 这是"证据验证"而非"我跑过一遍"的分界线。

### 一个我特意加的边界测试

规则 C1 的阈值是"离网率 >= 1.50"，我在 T2 里构造了 `1.50`（恰好等于）和 `1.49`（差一点）两个用例：

```
1.50 → 命中 C1（high）   ✅ 通过
1.49 → 不命中            ✅ 通过
```

**理由**：这类"看上去一样"的边界，是 AI 生成代码最容易写错的地方（把 `>=` 写成 `>`）。测试不覆盖边界，就等于没有测试。

## 十一、AAR 与版本标识

### 版本标识（两套，别混）

| 类型 | 值 | 用途 |
|---|---|---|
| **挑战版本** | `v0.5.5` | 平台侧挑战定义版本，提交时携带 |
| **应用版本** | `1.0.0` | 应用自身版本，`assets/agent.js` 中导出 |

两者是不同层面的东西：挑战版本变了不代表应用变了，反之亦然。本 README 同时记录，防止复核时对不上号。

### AAR（After Action Review）

**1. 学到什么**
- **Agent / Skill / RAG / 工作流不是四个并列名词，是一条有方向的链**：工作流定顺序 → Skill 给判断标准 → RAG 供依据 → Agent 做编排与自然语言出口。单独拿任何一个出来都不成立。
- **"会拒绝回答"比"总能给答案"更难做，也更值钱**。状态机里的 `off_topic`、字段缺口两种状态，是主动放弃给结论，而不是兜底猜一个。
- **确定性引擎 + 自然语言层分离**：数字全部由代码算，模型只负责把算好的结果讲成人话。这样即使语言层出错，数字也不会错。

**2. 与 AI 协作的经验**
- **让 AI 先写测试，再写实现**，边界用例（恰好等于阈值）必须显式要求，否则它默认只测"明显通过"的情况。
- **AI 会悄悄改口径**：中途它把"7 节点流程"改成了"9 步"却没同步文档，是我对着代码数出来的。所以文档里的每个数字都要能追到代码行。
- **不要让它一次性生成大文件**：分块写、每块验证，比一口气吐 500 行可靠得多。

**3. 卡点与突破**
- **卡点**：一度想把"原因假设排序"交给模型判断，结果每次排序不一样，无法测试。
- **突破**：改成"证据加权打分"的确定性算法后，排序稳定可测。**凡是需要测试的地方，就不能交给模型。**

**4. 改进方向**
- 数据只有 1 期周报，趋势判据的说服力有限，应扩到 8-12 周。
- RAG 检索目前是关键词匹配，没做向量召回，跨表述的语义问题会漏。
- 错误归因的"责任落点"还停留在部门级，没到具体的可执行动作。

### 自评

| 维度 | 自评 | 依据 |
|---|---|---|
| 可独立打开 | 通过 | 纯静态，无构建、无外部依赖，双击 `index.html` 即可 |
| 四类资产关联 | 通过 | 第五、六章给出链式关系与实现位置 |
| 证据可验证 | 通过 | 43 条测试，一条命令复现 |
| 数据边界 | 通过 | 全部脱敏合成数据，第四章写明不能做什么 |

**已知不足**：本交付为流程试点，数据为合成样本，结论不可用于真实经营决策。
